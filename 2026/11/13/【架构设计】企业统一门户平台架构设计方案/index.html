企业统一门户平台架构设计方案

本方案按照正式企业级项目的标准进行设计，覆盖需求分析、业务流程、系统架构、功能模块、数据库、Redis、Token 生命周期、跨系统认证、前后端接口、安全设计、部署架构、异常处理和测试验收。

一、项目背景与需求分析

1.1 项目背景

企业内部通常存在多个独立业务系统，例如：

  • 智能问答系统
  • 数据分析系统
  • 文档管理系统
  • 业务管理系统
  • 视频监控系统
  • 流程审批系统

这些系统可能由不同团队开发，拥有各自的访问地址和认证方式，用户需要记住不同的访问入口，管理人员也需要分别维护各系统的访问配置。

因此，需要建设统一门户平台，将各业务系统集中到一个入口，通过统一认证、统一服务管理和统一访问控制，实现业务系统的集中接入。

1.2 核心需求

需求一：统一认证

用户访问门户时，系统获取客户端 IP，根据 IP 和服务访问规则进行认证。

认证规则：

  1. 默认 Token 有效期为 1 小时。
  2. 管理员可以针对每个业务服务设置独立的 Token 有效期。
  3. 如果服务没有设置自定义有效期，则继承全局默认值。
  4. 每个 IP 对每个服务每天默认只能申请一次 Token。
  5. Token 到期后，当天不能再次申请。
  6. Token 过期时，提示用户：访问期限已到，请联系管理员。
  7. 每天 00:00 重置每日申请资格。
  8. 每个业务系统都可以调用统一认证中心验证 Token。

需求二：门户服务管理

管理员可以动态配置门户卡片。

卡片配置内容：

  • 服务名称
  • 服务编码
  • 服务图标
  • 服务描述
  • 服务跳转地址
  • Token 有效期
  • 每日申请次数
  • 是否绑定 IP
  • 是否允许续期
  • 卡片排序
  • 是否启用

需求三：业务系统跳转

用户进入门户后，能够看到具有访问权限的业务系统卡片。

点击卡片后：

  1. 门户获取服务配置。
  2. 检查用户/IP 是否具备申请资格。
  3. 获取该服务的 Token 策略。
  4. 签发对应服务的 Token，或者复用已有有效 Token。
  5. 生成一次性 Ticket。
  6. 跳转到目标业务系统。
  7. 业务系统使用 Ticket 向认证中心交换授权。
  8. 业务系统建立本地会话。
  9. 后续访问由业务系统和统一认证中心共同控制。

1.3 核心业务规则

首先明确本方案采用的业务规则：

规则 默认配置 是否可配置
全局 Token 有效期 60 分钟 是
服务 Token 有效期 继承全局配置 是
每日申请次数 1 次/IP/服务 是
每日重置时间 00:00 是，建议固定时区
Token 绑定 IP 开启 是
Ticket 有效期 60 秒 是
Token 是否允许续期 否 是
Token 是否允许主动撤销 是 是
Token 是否跨服务使用 否 否

注意：每日申请次数和 Token 有效期是两个独立概念。

例如：

  • 智能问答配置 30 分钟有效期，每天只能申请一次。那么用户 09:00 获得 Token，09:30 过期后，当天不能再次申请。
  • 如果数据分析配置 4 小时有效期，则用户可以在 4 小时内访问数据分析，但不会影响智能问答的访问。

  • 配置卡片展示顺序。
  • 访问异常记录。

3.3 统一认证模块

核心功能：

3.4 权限管理模块

  1. 用户权限：哪些用户可以访问哪些服务。

  3. 服务权限：Token 是否允许访问当前服务。

权限判定：

\[ Allow = UserAllowed \land IPAllowed \land ServiceEnabled \]

如果暂时没有用户体系，可以先实现 IP + 服务权限，但要预留用户 ID 字段。

  • 异常服务

需要记录：

重点记录失败原因，以便后续分析用户无法访问的原因。

四、核心认证机制设计

4.1 认证模型

认证分为两个层次：

  • 第一层：门户访问会话

用户进入门户后，建立门户自己的会话，负责用户身份识别、门户权限控制和卡片展示。

  • 第二层：业务服务 Token

用户点击某个业务卡片时，系统为该服务签发独立 Token。

这样可以避免所有业务系统共用一个 Token。

结构：

门户会话本身建议使用 HttpOnly Cookie，不能直接复用业务服务 Token。

4.2 Token 类型选择

使用随机不透明 Token，而不是直接使用 JWT。

原因：

  • Token 需要统一撤销。
  • Token 有独立的服务有效期。
  • 每日申请资格需要集中控制。
  • 需要即时判断服务权限。
  • 多个业务系统需要统一认证。

随机 Token 生成：

生成的 Token 有 256 bit 随机熵，足以抵抗暴力猜测。

Redis 和数据库只保存 Token 哈希值，原始 Token 只在签发和安全交换过程中短暂使用。

4.3 Token 生命周期

Token 生命周期：

注意：每日申请限制占用的是签发资格，而不是每次点击卡片都重新占用。

同一个服务重复点击时：

  • Token 仍然有效：复用已有授权。
  • Token 已经过期：提示访问期限已到。
  • Token 被管理员撤销：拒绝访问。
  • 第二天：重新获得申请资格。

4.4 Token 有效期计算

\[ ExpiresAt = IssuedAt + ExpireMinutes \times 60 \]

配置优先级：

必须保存签发时的有效期快照。

比如：

  • 09:00 签发 Token，有效期 60 分钟。
  • 09:30 管理员修改配置为 120 分钟。
  • 该 Token 仍然 10:00 过期。
  • 下一次签发才使用 120 分钟。

这样可以避免服务配置变化影响正在使用的业务系统。

五、完整业务流程设计

5.1 用户访问门户流程

  1. 用户访问门户

    浏览器请求门户首页。

  2. 获取访问 IP

    Nginx 从可信代理链获取真实客户端 IP。

  3. 门户身份认证

    有用户账号体系时验证用户身份；无账号体系时按配置执行 IP 准入。

  4. 建立门户会话

    使用安全 Cookie 保存门户会话。

  5. 获取服务卡片

    根据用户权限返回可访问的业务服务。

5.2 点击服务卡片流程

  1. 用户点击服务

    前端传递 serviceCode。

  2. 服务配置查询

    查询服务是否启用，以及 Token 有效期。

  3. 访问权限检查

    校验用户、IP 和服务权限。

  4. 查询 Token

    检查当前用户/IP + 服务是否已经存在有效 Token。

  5. 签发或复用 Token

    首次申请签发；重复点击复用有效授权。

  6. 创建一次性 Ticket

    生成 60 秒有效的随机授权码，绑定服务、Token 和跳转地址。

  7. 跳转业务系统

    通过 POST 表单提交 Ticket。

  8. 业务系统兑换 Ticket

    服务端通过认证中心交换授权，建立本地 Session。

5.3 跨系统认证时序图

5.4 Token 过期流程

当 Token 过期时：

  1. 业务系统访问认证中心。
  2. 认证中心判断 Token 已过期。
  3. 返回 40101。
  4. 业务系统清理本地 Session。
  5. 前端跳转到过期提示页面。
  6. 用户点击返回门户。
  7. 当天申请资格仍然被占用，不能重新签发。
  8. 提示联系管理员。

请求：

返回：

业务系统使用 grantId 关联自己的本地 Session。

注意：grantId 只是授权记录标识，不是可以独立使用的认证凭证。

业务系统每次需要校验授权时，使用自己的服务端身份调用认证中心，传递 grantId。认证中心根据授权记录进行验证。这样不需要把原始 Token 明文保存或暴露给浏览器。

如果未来业务系统希望直接使用 Bearer Token，也可以在 Ticket 交换时由认证中心签发独立的服务访问 Token，并且将它绑定到原始 grant 的过期时间和撤销状态。

10.2 业务系统接入流程

10.3 业务系统每次请求如何校验

  • 本地 Session 保存 grantId、serviceCode、expiresAt。
  • 每次请求先检查本地过期时间。
  • 使用短时间授权状态缓存，例如 10～30 秒。
  • 管理员撤销 Token 时，通过 Redis Pub/Sub 或消息通知主动清除相关缓存。
  • 高安全级别接口可以强制实时查询认证中心。

注意：明确安全边界，如果使用 30 秒缓存，撤销操作可能存在最多约 30 秒的传播延迟。要求即时撤销的系统不能依赖普通短缓存。

另外，业务系统的本地 Session 必须设置：

\[ SessionExpiry \leq GrantExpiry \]

不能让本地 Session 的过期时间超过授权过期时间。

十一、安全设计

统一门户虽然业务逻辑不复杂，但它相当于企业所有业务系统的统一入口，因此安全设计非常重要。

11.1 IP 获取安全

Nginx 配置：

Spring Boot 只能信任来自指定代理的 IP 转发头。

不能直接信任用户自己构造的 X-Forwarded-For，否则用户可以伪造 IP 绕过每日申请限制。

11.2 Token 安全

采用以下措施：

安全措施 具体实现
高强度随机数 SecureRandom，至少 256 bit
Token 哈希 SHA-256
Token 传输 HTTPS
Token 存储 Redis、MySQL 仅保存哈希
Token 过期 服务独立有效期
Token 撤销 维护授权状态
服务隔离 serviceCode 绑定
IP 绑定 签发 IP 与请求 IP 比较
防重放 Ticket 一次性消费
敏感信息 日志脱敏

11.3 Ticket 安全

Ticket 必须满足：

  1. 随机生成，不能通过递增 ID 生成。
  2. 有效期默认 60 秒。
  3. 只能使用一次。
  4. 必须绑定目标服务。
  5. 必须绑定业务系统客户端身份。
  6. 只能从指定业务系统兑换。
  7. 兑换成功后立即失效。
  8. Ticket 不得出现在 URL Query 参数中。

建议使用 Redis Lua 实现原子消费：

实际实现时，建议通过 Lua 完成读取、校验和删除的原子操作，并将 Ticket 绑定的 grantId 一并返回。

11.4 服务跳转安全

这是一个容易遗漏的安全问题。

假设管理员配置了：

如果允许普通用户修改跳转地址，可能造成开放重定向，甚至将 Ticket 泄露到恶意网站。

采用：

  • 跳转地址只能由管理员配置。
  • 限制 HTTPS 地址。
  • 禁止 javascript: 等危险协议。
  • 对域名进行白名单校验。
  • Ticket 只能兑换到指定服务。
  • 禁止用户提交任意跳转地址。

11.5 管理后台安全

建议采用 RBAC：

角色 权限
超级管理员 所有管理功能
服务管理员 管理指定服务
审计人员 查看日志、Token 记录
普通用户 访问授权服务

管理员修改 Token 有效期、每日申请次数、服务地址时，必须记录修改前后内容。

十二、异常处理与高可用设计

12.1 核心异常场景

异常场景 处理策略
Token 不存在 返回 40102
Token 过期 返回 40101
Token 被撤销 返回 40103
IP 不匹配 返回 40301
服务编码不匹配 返回 40302
服务已禁用 拒绝访问
每日申请次数已用完 提示联系管理员
Ticket 过期 重新发起跳转，但不重新签发 Token
Ticket 重复使用 拒绝兑换
Redis 不可用 认证失败，告警
MySQL 不可用 停止新授权签发，已有授权按安全策略处理
认证中心不可用 高安全业务默认拒绝访问

12.2 Redis 与 MySQL 一致性

假设：

  1. Redis 成功写入每日申请记录。
  2. Token 写入 Redis 失败。
  3. MySQL 写入也失败。

就会出现用户已经占用了每日申请资格，但实际上没有获得 Token 的情况。

使用状态机：

处理过程：

  1. 生成唯一 requestId。
  2. MySQL 创建 INIT 申请记录。
  3. Redis 原子占用每日申请资格。
  4. 保存 Token 哈希及状态。
  5. 更新申请记录为 ISSUED。
  6. 只有 ISSUED 状态才允许创建 Ticket。

如果第 3～5 步失败：

  • 记录失败原因。
  • 执行补偿。
  • 对已经失败的申请释放资格，或者由管理员处理。
  • 通过定时任务检查长时间处于 RESERVED 的申请记录。

Redis Lua 只能保证 Redis 内部操作原子性，不能代替 MySQL 事务。

12.3 高可用部署

组件 部署策略
Nginx 双节点负载均衡
Portal Service 至少 2 个实例
Auth Service 至少 2 个实例
MySQL 主从或高可用集群
Redis Sentinel 或 Cluster
业务系统 独立部署
日志服务 集中式日志管理

12.4 认证中心性能优化

认证中心是整个系统的关键服务，需要重点考虑：

  • Token 校验接口无状态化。
  • Redis Pipeline 批量查询。
  • 服务配置使用本地缓存 + Redis 缓存。
  • 对相同 grantId 的重复校验进行短时缓存。
  • 使用连接池管理数据库和 Redis。
  • 限制单个 IP 的认证请求频率。
  • 对认证接口进行独立监控。

设计性能目标：

指标 初期目标
Token 校验 P95 小于 100ms
Ticket 兑换 P95 小于 200ms
门户首页 P95 小于 500ms
服务签发 P95 小于 200ms
认证服务可用性 99.9%

在实际硬件、网络和并发规模下压测确认。
